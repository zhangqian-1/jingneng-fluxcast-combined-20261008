## 四、需业务方确认/解决的问题

### 问题 1（阻塞项）：康保风电预测值超过装机容量，算法按规则拒绝计算

**现象**：以真实数据原样透传时，算法对所有场站请求返回：

```
INVALID_RENEWABLE_FORECAST：
farmId=1 第1点预测值 157.955 MW 超过装机容量 150.800 MW
```

**数据依据**：

- 康保风电场（farmId=1）在《京津冀场站现有功率预测系统数量统计-含测点.xlsx》中的装机容量为 **150.8 MW**；
- 2026-09-18 08:00 批次预测 2026-09-19 首个时段（00:00–00:15）功率为 **157.955 MW**，超容量 7.16 MW（约 4.7%）；
- 其余 18 个场站首日 96 点全部在各自装机容量以内。

**影响**：算法按"预测功率不得超过装机容量"做硬校验，超限即拒绝计算。**若容量口径不解决，上线后每天的首个调度周期都会失败。**

**请确认**：

1. 康保风电场的实际装机容量是否已扩容（150.8 MW 是否为最新值）？
2. 预测系统内部使用的容量上限是多少？预测值允许超过额定容量吗？建议算法对类似异常进行处理（见问题5）

### 问题 2（阻塞项）：预测数据的时间口径与调度算法相差 15 分钟

**现象**：两边对"一个数据点属于哪个时刻"的定义不同：

| | 预测系统 | 调度算法 |
|---|---|---|
| 首日第 1 点 | `predictedTime = 202609190015` | 帧时间 `2026-09-19 00:00:00` |
| 首日最后 1 点 | `predictedTime = 202609200000` | 帧时间 `2026-09-19 23:45:00` |
| 口径 | **结束时刻**：00:15 的点代表 00:00–00:15 这 15 分钟 | **开始时刻**：00:00 的帧代表 00:00–00:15 这 15 分钟 |

即预测系统的 `00:15` 点 = 调度算法的 `00:00` 帧，**整体相差 15 分钟**。本次测试由算法侧适配层做了"减 15 分钟"转换后链路才跑通。

**影响**：如果平台或预测系统不统一这个口径，直接把 `predictedTime` 当作时段开始时刻使用，全天 96 点将整体错位 15 分钟，**负荷高峰/低谷会错配**，调度结果失去意义且不易察觉。

**建议**：口径转换由**算法侧**完成——预测系统维持现有 `predictedTime` 结束时刻口径，平台原样透传给算法，算法从 `renewable_data` 里提取时做统一的"减 15 分钟"转换。转换规则已在问题 4 的平台/算法分工中明确，各方对接时只需理解这个差异的存在。

### 问题 3：预测批次发布时刻需确认

**现象**：本次验证 `batch=202609180800`（09-18 08:00 发布）可抓到次日 96 点预测，推测系统**每天 08:00 发布一批**短期预测（含未来 10 天，timeSeries=1 为次日）。

**请确认**：

1. 批次是否每天固定 08:00 发布？是否存在其他批次（如凌晨 00:15 批次）？
2. 日前调度依赖"每天一批、覆盖次日 96 点"，若当天批次缺失或延迟，应急流程是什么（沿用上一批次？人工介入？）

### 问题 4：新能源预测数据透传契约（初步方案，后期可一块讨论修改约定）

**约定**：平台作为**通道**，从预测系统无差别获取新能源数据，原样附加到每站请求体中；算法侧负责全部数据处理（格式解析、口径转换、聚合、校验）。

**请求体格式**：

```json
{
  "point_table": ["GARD_11MBY0100000BJ01XQ01", "..."],
  "frames": [
    { "timestamp": "2026-09-19 00:00:00", "GARD_11MBY0100000BJ01XQ01": 125.3 }
  ],
  "renewable_data": [预测系统原始返回，第一段描述的长表格式]
}
```

**三方职责与交互流程**：

| 阶段 | 预测系统 | 平台 | 算法 |
|---|---|---|---|
| 获取数据 | 维持现有 API：`GET /externalData/shortTermForecastsData?farmId={id}&batch={batch}` 返回长表（farmId、predictedTime 结束时刻、predictedPower、timeSeries、batch）| **调用预测系统 API**：每天一次按 `batch` 号和 19 个 farmId 逐个查询，汇总结果暂存 | - |
| 组装请求 | - | 按 source_id 逐站构造燃机请求体，在每站都附加相同的 `renewable_data` 字段（包含上一步的全部预测结果）| - |
| 处理数据 | - | - | 从 `renewable_data` 提取：解析长表、取 `timeSeries=1`（次日 96 点）、`predictedTime` 减 15 分钟转开始时刻、按 farmId 聚合成宽表、逐 farmId 校验容量、与 `frames` 时间轴逐点对齐 |

**平台侧处理细节**：

1. **何时获取**：每天预测系统发布批次后立即获取（建议 08:30，预留发布延迟）；若某天批次延迟或缺失，应用前一天 batch，并记录异常告警
2. **怎么获取**：依次调用预测系统 API `shortTermForecastsData?farmId=1&batch=YYYYMMDDHHMM`、`farmId=2&batch=...`...`farmId=29&batch=...`，共 19 次；每次返回 960 条（10 天数据）
3. **怎么组装 `renewable_data`**（这是关键）：
   - 预测系统单次查询返回格式（farmId=1）：
     ```json
     {
       "code": 200,
       "msg": "success",
       "data": [
         {"farmId": 1, "predictedTime": "202609190015", "predictedPower": 157.955, "timeSeries": 1, "batch": "202609180800"},
         {"farmId": 1, "predictedTime": "202609190030", "predictedPower": 149.334, "timeSeries": 1, "batch": "202609180800"},
         ...
       ]
     }
     ```
   - 平台把所有 19 个 farmId 的 `data` 数组合并为一个，作为 `renewable_data` 字段值：
     ```json
     "renewable_data": [
       {"farmId": 1, "predictedTime": "202609190015", "predictedPower": 157.955, "timeSeries": 1, "batch": "202609180800"},
       {"farmId": 1, "predictedTime": "202609190030", "predictedPower": 149.334, "timeSeries": 1, "batch": "202609180800"},
       ...（farmId=1 全部 960 条）...,
       {"farmId": 2, "predictedTime": "202609190015", "predictedPower": 0.0, "timeSeries": 1, "batch": "202609180800"},
       ...（farmId=2 全部 960 条）...,
       ...（farmId 3~29 依次追加）...
     ]
     ```
   - 即：**所有 19 个 farmId 的结果行拼在一起，去掉 `code`/`msg`，只保留 `data` 数组元素**
4. **怎么暂存**：所有 19 个 farmId 的结果合并后存储（上述 `renewable_data` 值），关键字为 batch ID；同一 batch 在该天内保持不变
5. **怎么附加**：在**所有 7 站**的请求中都附加相同的 `renewable_data` 值（即当前 batch 的完整合并结果），确保聚合时新能源数据一致

**契约要点**：

| 项 | 约定 |
|---|---|
| 预测系统 API | `GET /externalData/shortTermForecastsData?farmId={1..29}&batch={YYYYMMDDHHMM}`，返回格式：`[{farmId, predictedTime, predictedPower, timeSeries, batch, ...}]` |
| 新能源数据 | 作为 `renewable_data` 字段原样透传；平台不理解其业务语义，只做机械复制 |
| 到达算法时 | farmId、predictedTime（结束时刻）、predictedPower、timeSeries 等原生字段保持，算法侧完全消化 |
| 时间轴口径 | 预测系统维持结束时刻（00:15 起），算法侧负责 -15 分钟转换为开始时刻（00:00 起） |
| 批次选择 | 平台负责确定当天 batch ID，算法侧只消费；批次缺失时的回退策略待定 |

**待定项**：

1. 平台怎么确定每天的 batch ID（平台按约定时刻查询）？
2. 平台获取数据失败或延迟时的应急流程（使用前一天 batch、告警、手工介入）？
3. `renewable_data` 字段在 19 个 farmId 的请求中是否都要包含（推荐：是，确保任意站缺失都不阻塞聚合）？

### 问题 5：数据异常时的计算结果处理

**场景**：算法检测到多种数据异常时的处理策略。包括：

1. **缺失数据**：燃机测点或新能源预测字段缺失 → 直接拒绝
2. **空值数据**：测点值为 `null`、`NaN` 或无穷大 → 直接拒绝
3. **异常值数据**：测点值为负数/超限值 → 直接拒绝
4. **缺失场站**：某个 farmId 的预测数据未返回 → 直接拒绝

**现有行为**：算法对所有异常采用硬拒绝（返回 422）

**建议改造**：采用**明确的失败策略**

| 异常类型 | 当前行为 | 建议改造 | 理由 |
|---|---|---|---|
| 新能源某 farmId 缺失 | 422 拒绝 | **跟缺失值相关的计算结果返回空值** + 日志记录缺失 farmId | 不能补零隐藏问题，平台需知道为何算不了 |
| 新能源某 farmId 全空值 | 422 拒绝 | **跟缺失值相关的计算结果返回空值** + 日志记录哪个 farmId 全空 | 同上，可能是上游查询失败 |
| 燃机测点空值 | 422 拒绝 | **跟缺失值相关的计算结果返回空值** + 日志记录缺失测点 | 同上 |
| 其他数据异常（如数值为负值、超限等） | 422 拒绝 | **跟异常值相关的计算结果返回空值** + 日志记录异常测点 | 同上 |

### 问题 6：Gurobi 求解器

- 算法联合优化依赖 Gurobi 商业求解器。本地开发机许可证已于 2024-10-28 过期，本次测试**最终求解步骤未实际执行**（求解前各环节均已验证）。
- 生产环境为 ARM 架构（Kylin V10 SP3 aarch64），**许可证与 x86 不通用**，不保证内网 Gurobi 可用性。
