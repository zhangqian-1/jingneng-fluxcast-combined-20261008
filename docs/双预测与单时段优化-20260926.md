# 双预测与单时段优化（2026-09-26）

用户要求原来的长时段预测与给优化用的单点预测都保留，并再次明确优化不需要长时段。本次结构如下：

- 单点预测：历史实测 → 下一15分钟的1点预测 → 单时段优化。
- 长时段预测：历史实测 → 未来24小时的96点预测 → 独立提供给平台，不进入优化。

两套原预测均为七站合计发电功率预测。新能源19场站的预测数据由平台通过renewable_data传入，算法不主动调用新能源接口；FORECAST_BASE_URL只指向七站单点预测。此分工已按2026-09-27对接要求再次确认，见[来源说明](新能源数据来源确认-20260927.md)。

## 调用方式

| 服务 | 默认地址 | 请求 | 输出 |
|---|---|---|---|
| 平台联合计算 | POST http://127.0.0.1:18768/api/v1/fluxcast/compute | point_table、frames、renewable_data，保持原约定 | 下一15分钟29个结果点 |
| 单点预测初始化/查询计算 | POST http://127.0.0.1:18768/api/v1/fluxcast/forecast/compute | 原预测point_table、frames | 下一15分钟1点，未就绪返回200空结果及原因 |
| 原24小时预测 | POST http://127.0.0.1:18780/api/v1/fluxcast/compute | 原预测point_table、frames | 未来96点，未就绪返回200空结果及原因 |
| 原24小时最近结果 | GET http://127.0.0.1:18780/api/v1/fluxcast/compute/latest | 无 | 最近成功的96点；无记录返回404 |

优化入口的字段、事件标识、结果格式不变，不新增模式字段或长优化入口。两个预测服务采用各自原版接口，依靠不同服务地址区分；不把同名路径的两种响应混在一起。长预测收到请求不会调用优化，优化代码的FORECAST_BASE_URL始终指向forecast单点服务。

直接调用原预测时必须使用原测点编码（保留点号和冒号），35个测点完整；不使用平台优化入口支持的点号转义。两套原预测均使用UTC时间，原版请求为96帧连续历史实测，不接收未来96帧。长预测首点为历史末帧后15分钟，末点为后24小时。业务量为七站合计发电功率，不是独立用户侧负荷。

## 启动与部署

解压完整20260926-r3交付包，Windows运行start.ps1，Linux运行sh start.sh。启动脚本加载两套原始预测镜像和优化镜像，并等待三个服务健康；无需主机安装Python或unzip。包为Linux/amd64，ARM整包实机验收仍未完成。

优化端口默认18768，长预测端口默认18780。Linux分别通过DISPATCH_PORT、DAY_FORECAST_PORT调整；Windows通过-Port、-DayForecastPort调整。默认监听本机，长预测的局域网绑定通过DAY_FORECAST_BIND或-DayForecastBindAddress配置，优化绑定使用原DISPATCH_BIND或-BindAddress。

旧8步滚动和96步优化不恢复。页面仍为固定历史试算展示，上排累计、下排当前。现场启停状态、康保容量差异、购电条件及目标ARM服务器验收边界继续保留，详见既有接口文档。

## 与用户MD的逐项核对

优先依据第一份[平台接口约定](requirements/platform-contract-20260919.md)，其余两份仅补查未冲突要求。下面是当前平台联合计算接口的约定；独立长预测继续采用原作者接口，不要求平台把优化请求改成另一种格式。

| MD要求 | 当前实现与验证 |
|---|---|
| POST /api/v1/fluxcast/compute | 路径不变，全七站一次请求、一次返回 |
| point_table、frames、renewable_data | 仅这三个必填顶层字段，不新增mode或horizon |
| 96帧、每15分钟一帧 | 按用户明确的历史实测、末帧当前处理；优化目标为末帧后15分钟 |
| 新能源保持原始长表 | 合并19场站data数组，保留farmId、predictedTime、predictedPower、timeSeries、batch |
| timeSeries=1、结束时刻转开始时刻 | 减15分钟，转换为UTC并与下一预测目标对齐，逐场校验容量 |
| event_key与result_point | 固定JNH.Fluxcast.Compute；27个出力及objectiveYuan、carbonTon，共29个点 |
| value为浮点、组合唯一 | 成功结果为有限float，varname与timestamp组合唯一 |
| 时间格式与UTC保持一致 | 返回下一目标时刻，保留输入的空格/T、UTC后缀及小数精度 |
| 原始测点与转义 | 联合入口兼容点号转义，调用原预测前恢复原编码；不改原作者接口 |

上述约定由tests/test_platform_contract.py、tests/test_platform_config.py与真实容器HTTP联调共同核对。原MD下方残留的逐站source_id及“与历史frames逐点对齐”文字，仍按用户已确认的全场站、下一时段解释执行，详见[依据说明](requirements/README.md)。

两套模型分别需要3天和7天历史才能首次出结果；每次请求仍是96帧。历史不足返回等待原因，不能以空结果当作优化成功。两个预测服务的缓存独立，长预测不参与优化就绪判断。
