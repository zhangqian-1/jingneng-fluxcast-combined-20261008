# 单点与96点预测历史补传说明

老师，新版联合部署包增加了96点历史补传接口。更新部署后，您可以通过原联合服务的服务器地址和端口分批传入数据，不需要进入容器，也不需要另行提供取数接口。

单点预测的补传入口原来已经存在，两种入口如下。本文保留原文件名和链接。

| 用途 | POST路径（均使用原联合服务公开端口） | 最少连续历史 |
| --- | --- | --- |
| 单点预测初始化，响应为下一15分钟的1点 | `/api/v1/fluxcast/forecast/compute` | 288点，约3天；也会尝试更新96点缓存 |
| 只给96点预测补历史，响应为未来96点 | `/api/v1/fluxcast/day-forecast/compute` | 672点，约7天；不调用单点预测 |

两个接口均提交 `point_table + frames`，每批96帧，不需要 `renewable_data`。以下第1—4节说明96点补传，第5节说明单点补传及两者的顺序。

## 1. 调用地址

```text
POST http://服务器地址:实际对外端口/api/v1/fluxcast/day-forecast/compute
Content-Type: application/json
```

默认宿主机端口为 `18768`，现场使用其他端口或网关时，以实际配置为准。仍是一个联合容器、一个公开端口，8002无需对外开放。

**须先更新到包含此接口的新镜像。旧镜像没有这个路径，调用会返回404。**

部署默认只绑定服务器本机 `127.0.0.1`。如果原联合接口已经通过网关对外提供服务，请在同一个网关转发此新路径，并沿用已有访问控制。如果在内网直接调用，启动新包时把 `DISPATCH_BIND` 设置为服务器可访问的内网IP，例如在Linux中执行：

```bash
export DISPATCH_BIND='替换为服务器实际内网IP'
export DISPATCH_PORT=18768
sh start.sh
```

在解压后的完整部署包目录执行，保持原Compose项目名和持久化卷配置，避免升级时意外切换数据卷。网络侧须允许调用方访问该端口；不要把IP示意文字原样执行。

## 2. 本次旧缓存如何处理

部署人员先暂停平台调用并停止联合容器，在 `/opt/forecast-day/runtime` 对应的持久化目录或数据卷中备份移走下面两个文件，再启动新镜像：

- `history_7station_2025_v1_utc_to_asia_shanghai_v1.csv`
- `latest_forecast_utc_to_asia_shanghai_v1.json`

保留目录及写入权限，单点预测、调度及实测归档数据不动。补传完成前暂停正常实时请求，避免最新数据先进入96点缓存，使更早批次被拒绝。新接口不会自动删除缓存，也不会绕过缓存规则校验。

## 3. 如何发送7天历史

从历史库取7天连续原始测点数据，每15分钟一帧，共672帧。按时间先后分成7批，每批96帧，上一批响应后再发送下一批。

每批请求只有 `point_table` 和 `frames`，不需要 `renewable_data`：

| 字段 | 要求 |
| --- | --- |
| `point_table` | 七站全部35个原始测点编码，保留点号和冒号；清单见同目录 `forecast-measurement-points.csv` 的 `raw_name` 列 |
| `frames` | 恰好96帧，批内及批间按时间顺序连续，每15分钟一帧 |
| 每帧内容 | `timestamp` 及对应35个测点的原始值，沿用原接口单位；真实缺测用 `null` |
| `timestamp` | UTC时间，例如 `2026-10-01T00:00:00Z`；北京时间数据先转换成UTC |

请求结构参考部署包 `service/examples/day-forecast-request.json`，其中是归档样例数据，实际补传须替换为现场真实数据。

将第一批完整请求保存为 `batch01.json`，在能访问服务器的电脑执行：

```bash
curl --fail-with-body --max-time 300 -X POST "http://服务器地址:实际对外端口/api/v1/fluxcast/day-forecast/compute" -H "Content-Type: application/json" --data-binary "@batch01.json"
```

Windows PowerShell请使用 `curl.exe`。随后依次发送 `batch02.json` 至 `batch07.json`。服务器地址、端口和文件名替换为实际值。

为使联合接口能生成当天00:00—23:45曲线，先补齐截至北京时间前一天23:45的完整7天，再按时间顺序补到最新；继续补传时每批仍为96帧，可采用末点逐次向前推进的滑动窗口。

## 4. 如何判断成功

- `reason=history_not_ready`、`result_point=[]`：当前历史不足，本批已缓存，继续补下一批，不要清缓存。可查看 `continuous_points` 和 `required_points`（672）。
- `reason=weather_history_not_ready`：温湿度历史尚不足，应补齐真实历史；7批是最低历史长度，不能保证缺天气时也能预测。需要回补更早历史时，应重新从空96点缓存按时间顺序导入。
- 成功时，`result_point` 中有96条 `varname=totalPowerForecast` 的预测记录，同时返回 `forecastPointCount`、`forecastIntervalMinutes`，`extra_info` 中返回批次及时间信息。**不要用数组总长度是否等于96判断。**
- 其他错误先按返回的 `reason`、`message` 或 `error_code`、`detail` 处理。HTTP 200本身不代表已完成预测。

补传成功后恢复原联合接口 `/api/v1/fluxcast/compute` 的正常调用，并核对当天曲线。新接口返回的是历史末帧之后的96点预测；它不执行调度、不更新实测归档，也不消耗当天曲线的发布机会。界面仍使用原联合接口返回的当天曲线。

三个算法保持原样，本次只增加96点服务的对外转发入口，完整返回该服务的响应。它不调用单点预测，适用于本次仅重建96点历史的情况。

## 5. 单点预测如何补3天历史

**单点接口已经由联合服务提供，无需为它新增接口或开放8001端口。** 从服务器外调用仍需原公开端口可达，或网关已转发下面的路径；仅在服务器上启动服务，不代表外部网络一定可达。

```text
POST http://服务器地址:实际对外端口/api/v1/fluxcast/forecast/compute
Content-Type: application/json
```

单点预测用过去3天历史预测下一个15分钟的1点，不是预测未来1天。它与96点使用不同缓存，补好96点不会自动补好单点。

### 发送方法

使用第3节相同的35个原始测点、UTC时间及JSON格式。从空单点缓存初始化时，至少连续发送3批，每批96帧，共288帧，时间从早到晚；温湿度历史也须满足要求。

```bash
curl --fail-with-body --max-time 300 -X POST "http://服务器地址:实际对外端口/api/v1/fluxcast/forecast/compute" -H "Content-Type: application/json" --data-binary "@single_batch01.json"
```

将文件名依次换为 `single_batch02.json`、`single_batch03.json`，等待每批响应后再发下一批。Windows PowerShell使用 `curl.exe`。

若现有缓存已满足3天且能正常预测，不必重新补。若日志是 `continuous=98 required=288`，只是当时连续历史不足，应沿已有缓存末点继续提交连续数据；不要从更早日期重新倒灌，也不要因为96点缓存规则变化就清空单点缓存。若必须回放早于单点缓存末端的数据，需要部署人员先备份并为单点安排独立空缓存，不能直接覆盖在线历史。

### 成功判断

- `reason=history_not_ready` 或 `weather_history_not_ready` 且 `result_point=[]`：尚未就绪，继续补齐连续真实历史或天气数据。
- 成功响应的 `result_point` 中有1条 `varname=totalPowerForecast`，时间为本批最后一帧之后15分钟，才表示单点预测已就绪。
- 不要只看HTTP 200或认为发满3批必然成功；已有98点也不能与任意其他历史直接相加，必须连续且可用。

### 两种历史都需要补时

原 `/forecast/compute` 会先提交单点；单点返回HTTP 200后，还会尝试把同批数据交给96点服务，但响应主体仍是单点结果。因此，**单点成功不能作为96点已补齐的判断依据**。

两套缓存都为空时，可先将7天历史的前4批发送到96点专用入口；后3批按时间顺序逐批发送到原单点入口，并在每批之后用相同批次调用96点专用入口核对96点状态。这样单点接收最后3天，96点积累完整7天。两边均成功后，再继续按时间顺序补到最新并恢复正常调用。

如果单点已正常、只是96点旧缓存不兼容，就只执行第1—4节。若单点已有部分较新历史，则按上述已有缓存规则继续积累，不要照搬“两套空缓存”的步骤回灌旧数据。现场两份缓存的末点未知时，应先由部署人员确认时间范围，再确定批次顺序。

日常运行仍调用原联合接口 `/api/v1/fluxcast/compute`；程序会继续更新预测缓存，无需每天重新初始化。此节仅补充调用说明，未修改单点算法和接口实现。
