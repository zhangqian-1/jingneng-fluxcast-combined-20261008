# 七站滚动调度接口（2026-09-22）

## 当前规则

实际值每15分钟上报一个断面。外部预测覆盖后续2小时的8个15分钟时段，内部联合求解8步，对外只返回最近一个待执行时段的建议。下一实际断面到来后再滚动一步。没有接入预测算法，不把已有实际数据复制成预测；没有接入电厂控制系统。

必需输入：实际运行状态、未来总负荷/供电计划、风光可用功率预测。可选输入：原调度计划，仅用于同一未来窗口的成本、碳排放对比。实际数据与预测数据分开：

- 燃机实际出力：决定本轮初始功率，运行状态/持续时间/当日启停次数决定跨时段约束。
- 风光实际出力：保存当前实测及供对比，不当成未来可用功率上限。低实际值可能来自限发。
- 不再要求燃机功率预测。燃机未来出力由优化器决定。原调度计划是原先安排的未来出力，不是当前实际出力；不能把当前实测复制8次作为真实原计划。
- 风光预测：外部提供的未来可用功率上限，优化决定接纳量。
- 总负荷预测/供电计划：**独立的总供电需求输入**，每时段必须满足“燃机 + 风光接纳 + 主网购电 = 总需求”。不允许通过主网售电平衡。

## 路径与触发

| 方法与路径 | 用途 |
|---|---|
| POST `/api/v1/fluxcast/rolling/actuals` | 上报实际断面，七站+19风光站 |
| POST `/api/v1/fluxcast/rolling/reference-plan` | 可选：上报未来8步原调度计划，仅用于比较 |
| POST `/api/v1/fluxcast/rolling/forecasts/renewable` | 上报19风光站未来8步可用功率预测 |
| POST `/api/v1/fluxcast/rolling/forecasts/demand` | 上报未来8步总负荷预测或供电计划 |
| GET `/api/v1/fluxcast/rolling/status/{snapshot_id}` | 查询该断面状态及当前有效首步建议，不触发新计算 |

三类必需输入可以任意顺序到达，通过`snapshot_id`关联。最后一类必要输入补齐时触发求解；缺少输入时返回202 `waiting_inputs`及`missing_inputs`。原计划不在缺失必需输入清单中；结果仍有效时也可补交原计划，只追加对比，不重新求解、不改变已发布建议或其生成时间。没有独立定时器反复调用旧数据：平台每15分钟提交新断面，新数据到齐就计算。

初版滚动路径`/forecasts/thermal`已撤销，调用返回404；请迁移到上述可选原计划结构。已有自然日96点接口不受影响。旧滚动数据库内的thermal_forecast输入不再参与新求解；已保存结果不自动重算，下一断面使用新规则。

实际曲线文件并不会因放入data目录自动变成实时上报。对接方须按以下结构推送，预测端点目前是可调用的输入接口，预测服务本身待外部接入。

## 时间与功率单位

所有接口时间均为UTC，可使用Z、明确偏移量或无时区日期时间（按UTC解释）。服务统一归一化UTC返回。实际断面必须在15分钟边界；首个预测时段为实际断面+15分钟，随后严格递增，共8点。

例如实际断面为10:00，计算完成后提前发布10:15–10:30的建议，内部预测窗口为10:15–12:15。10:15的新实际断面触发下一轮，预测窗口为10:30–12:30。尚未到达的实际时间、不及时送达以致生效时刻已过的断面拒绝参与新计算。求解完成已过生效时刻也不发布过期建议。

功率单位为MW。预测按15分钟区间功率输入；计算电量为功率×0.25h，是计划估算。首段爬坡校验连接测量值与下一边界目标，模型不模拟秒级跟踪轨迹；实际电量优先采用区间平均功率/电能计量，不能将瞬时实测×0.25h称为精确计量。

启停次数的运行日默认采用`Asia/Shanghai`，可用`ROLLING_DAY_TIMEZONE`配置。传输UTC与启停统计运行日是两回事；上游提供的starts_today/stops_today必须按此配置统计。

## 实际断面结构

```json
{
  "snapshot_id": "actual-20260921-1000",
  "timestamp": "2026-09-21T10:00:00Z",
  "thermal_mw": {"GARD": 300.0, "JFRD": 0.0, "JQRD": 0.0, "JXRD": 0.0, "JYRD": 0.0, "SZRD": 0.0, "WLRD": 0.0},
  "renewable_mw": {"1": 10.0, "2": 0.0, "3": 0.0, "4": 0.0, "7": 0.0, "8": 0.0, "10": 0.0, "11": 0.0, "12": 0.0, "13": 0.0, "16": 0.0, "17": 0.0, "19": 0.0, "20": 0.0, "21": 0.0, "22": 0.0, "23": 0.0, "28": 0.0, "29": 0.0}
}
```

上例允许保存实际功率，但缺少`thermal_state`时不会求解。`thermal_state`须覆盖七站，每站结构如下（这是字段示例，不是现成的七站状态数据）：

```json
{"running": true, "state_since": "2026-09-20T00:00:00Z", "starts_today": 0, "stops_today": 0}
```

`running`为布尔值；`state_since`为当前持续运行/停机状态的实际开始时刻；次数为非负整数。可以在同一snapshot_id保持时间、功率完全一致的前提下，补齐原先缺失的thermal_state一次。已有实际值或已有状态不得覆盖。停机却有明显出力、状态时间倒退、同一运行日启停次数清零等矛盾会被拒绝。

当日发生的当前状态切换必须计入对应启停次数，即使首次上报也不能遗漏。相邻有效状态相同但state_since更新，代表中间至少发生一次启停循环，同一运行日两项计数均须相应增加；新的切换时间不得早于或等于上一有效状态观测时间。中间某次上报缺少状态时，后续仍与最近一份完整状态核对，不因缺报而丢失历史。按配置运行日跨午夜时允许当日计数清零，state_since继续保留真实时刻。

## 预测结构

两类预测共同字段：`snapshot_id`、`forecast_id`、`issued_at`、`frames`。forecast_id是该类预测的版本编号，issued_at不得晚于服务当前时间，必须早于首时段。

- 风光frames：8项，每项`{"timestamp":"...","power_mw":{"1":20.0,...}}`，每项完整19站，JSON场站键为字符串farmId。
- 总需求frames：8项，每项`{"timestamp":"...","demand_mw":250.0}`。

上面省略号仅用于说明字段。可运行的完整示例由`examples/build_rolling_example.py`生成；示例是人工构造的联调数据，禁止当作现场实际或真实预测。

不能上传整数时间戳、字符串功率、布尔功率、null、NaN或无穷值。新滚动端点遇到这些值返回422，要求上游补齐有效数值；没有把旧96点接口的宽松数值修复行为默默搬到实时状态输入。

风光可用预测超容量时沿用已有容量修正规则：首点无前值时采用容量上限，后续异常采用上一有效预测值并记日志。实际风光值原样保存；原始预测输入也保留，只有求解使用修正后的序列。

## 可选原调度计划

公共字段为`snapshot_id`、`plan_id`、`issued_at`、`frames`。时间规则与预测一致。8项frames每项包含：

| 字段 | 含义 |
|---|---|
| `timestamp` | 与本轮预测对应的时段起点 |
| `thermal_mw` | 七站原计划出力，键为STATION_CODES，单位MW |
| `thermal_running` | 七站原计划运行状态，布尔值，用于核算启停费用 |
| `renewable_mw` | 19站原计划接纳功率，键为字符串farmId，单位MW |
| `grid_buy_mw` | 原计划主网购电功率，单位MW |

原计划须来自原调度安排。提供完整的燃机、风光及购电安排，避免由程序拼凑原计划。核算采用与优化相同的需求、风光可用预测、价格、排放系数及实际初始状态。检查供需平衡、可用风光上限、燃机出力/状态范围及购电上限；比较结果是经济核算，不代表对原计划全部跨时段约束的可执行性认证。

- 没有原计划：`comparison.status=not_provided`，仍有优化后的成本、碳排放，不返回基准值、节省值或虚构的0%改善。
- 原计划可比较：`comparison.status=available`，附`plan_id`，`step_metrics`包含`baselineCostYuan`、`baselineCarbonTon`、`costSavingYuan`、`carbonReductionTon`；`horizon_metrics`包含对应2小时合计`baseline_cost_yuan`、`baseline_carbon_ton`、`cost_saving_yuan`、`carbon_reduction_ton`。
- 格式合法但与当前窗口不匹配或不满足同口径条件：`comparison.status=unavailable`并附原因、写日志，不阻断正常优化、不覆盖有效指令。格式本身错误返回422，原有必需输入和结果仍保留。
- 差值统一为“原计划−优化计划”，允许为负，不保证必然减碳。百分比若由展示端计算，分母为0时不得显示0%或进行除零运算。
- 同一snapshot_id的原计划重复提交幂等，内容不同返回409，不覆盖已存计划。过期/已被新断面替代的结果不补算对比。

运行`python examples/build_rolling_example.py --include-reference-plan --output output/rolling-example-with-plan`可生成3份必要输入和1份可选原计划；全部是人工联调样例。

## 结果及版本

成功返回200，status为completed：

- `result_point`仅包含同一时间戳的27个功率值：七站`{CODE}_MW`、19站`farm_{ID}_MW`、`grid_buy_MW`。不将后7步作为可执行指令返回。
- `thermal_running`：同一首步的七站建议状态。
- `effective_at`、`valid_until`：本步建议生效及到期时刻。
- `horizon_end`：内部2小时预测窗口结束时间。
- `horizon_metrics`：本次2小时窗口的优化成本与碳排放预计值。**不能把相邻重叠窗口的这些合计相加**。
- `step_metrics`：仅发布首步的15分钟优化计划电量、成本、碳排放。计划累计需按有效时段去重，再累计首步指标；不等于实际计量。
- `comparison`：可选原计划的核算状态与比较结果，基准数值仅在比较有效时出现。
- `actual`、`forecast_ids`、`generated_at`：本轮实际输入和使用的预测版本信息。
- `step_minutes=15`、`horizon_steps=8`、`publish_steps=1`。

同一输入重复上报不重复求解。发布前可用更晚issued_at和新的forecast_id修订某类预测；发布后不覆盖该断面结果，必须进入下一断面。已有输入各版本和内部8步结果保存在SQLite，供审计，不自动向控制设备下发。

新实际断面到来后旧断面状态为superseded；已到期结果状态为expired。此时状态接口不再把旧result_point当作当前建议返回。求解失败状态为failed，记录错误和日志；发布前修订预测可触发重新计算。

## 约束与当前限制

- 复用HiGHS、站级出力上下限、爬坡、最小开停机时间、每日最多启停一次、仅购电，目标包含发电、购电、启停、弃电和碳排放成本。
- 初始功率使用实测值，不静默裁剪到运行下限；超出当前站级模型上限时要求核对参数，不伪造初值。
- 继承实际state_since，在未满足最小开停机时间前锁定状态；按运行日分组计算剩余启停次数，跨午夜重置当日预算，而非每次重算清零。
- 本版是站级短期滚动优化，**没有自动接入全天启停计划**。2小时窗口能继承已有开停机义务，但不足以评价新启动后最长6小时的全部成本或保证2小时以外可行；结果是调度建议，仍需长周期计划协调。
- 主网购电上限沿用既有模型：窗口峰值需求的20%。为不再依赖燃机预测，站间购电费用分摊权重固定为本轮实际燃机出力占比；全为0时等比分摊，窗口内不变，优化与原计划核算使用相同权重。这仅是结算建模假设，不是燃机出力预测、总负荷来源或已确认的实际结算规则。
- 碳排放成本仍进入优化目标（当前配置62.36元/tCO₂），滚动求解不再使用可选原计划碳排放作为硬上限；提交原计划与否不影响出力和优化成本。历史96点模式保留其原有基准碳约束。模型约束不可行仍会报错。
- 不接收无状态历史的首次调度，不擅自根据单点功率猜测持续时长。
- 现有全天看板仍是历史96点情景回放，不会因这些端点上线自动成为实时监控页面。

## 错误和运行配置

202表示必要输入未齐；409表示批次冲突、断面过时或结果被替代；422表示字段、时间轴或状态不合法；503表示求解、日志、配置或存储不可用。优化失败响应没有result_point；单独的原计划无法比较，不等于优化失败。详细原因写工作日志。

求解结束和比较核算完成后均检查首步生效期限，不发布已经错过生效时刻的新建议。补交原计划期间若原结果到期，则返回expired，不把到期出力重新返回为有效指令。超出日期表示范围的UTC换算或预测窗口统一返回422。

`ROLLING_DB_PATH`默认output/rolling.sqlite3，需可写并持久化。`WORK_LOG_PATH`沿用工作日志路径。求解在独立进程执行，求解器限时20秒，进程等待上限25秒；SQLite事务串行化同一数据库上的输入选择与结果发布，避免重复发布。数据库和日志目前没有自动轮转，部署时需要保留与备份策略。

旧`/api/v1/fluxcast/compute`保留原自然日96点协议，仅用于原有接入/历史回归，不自动改成8步协议。新平台滚动调用须使用本文路径，`/docs`可查看输入模型。
