# 七站实际值接入与滚动优化方案草案

> 此为讨论过程草案，已被用户后续决定及[最终接口说明](rolling-api.md)取代。最终采用15分钟实际上报、未来2小时8步前视、仅发布1步；现有曲线按实际材料保留，预测不再由历史实际曲线代替，总供电需求采用独立平台输入。草案中的固定全天启停计划衔接尚未接入，不应视为已实现。

日期：2026-09-21。状态：供确认的设计，接口与滚动求解尚未实现；现有全天接口继续按最新平台协议运行。

## 已确认需求

- 单独接收七个燃机场站和19个新能源场站的实际功率及采集时间。
- 现有页面中称作“实时出力”的96点原始曲线，在新功能中用作预测/未优化参考曲线；历史数据改名不等于已经建立功率预测模型。
- 实际出力、预测出力、优化计划是三类独立数据，不能互相覆盖。
- 用户最终确定：实际数据每15分钟上报一次，近期滚动窗口为未来2小时，即8个15分钟时段；这不等于新增了预测算法。
- 新功能仍为场站聚合调度；不擅自把场站级状态当作场内每台机组的真实状态。

## 推荐时间尺度

| 项目 | 推荐初始设置 | 说明 |
|---|---|---|
| 实测上报 | 每15分钟一次 | 七个燃机场站和19个新能源场站，带各自测量时间 |
| 滚动计算 | 每批完整有效的15分钟实测到达后触发一次 | 同批重传不重复计算；缺数据时不按定时器重复使用旧快照伪造新一轮 |
| 优化时段 | 15分钟 | 保留现有功率、电量、爬坡及成本核算粒度 |
| 近期优化窗口 | 未来2小时，8个时段 | 窗口每次向后移动15分钟，支持跨自然日 |
| 新计划生效 | 下一可执行的15分钟边界 | 给求解和发布留时间，明确生效时间；过期结果不追溯下发 |

按用户要求选择2小时窗口。当前参数中高安屯最小运行时间为6小时，其他站也有超过2小时的最小开停机时间；因此推荐保留长周期启停计划，2小时滚动层在该计划和实际状态约束下优化出力、新能源接纳及主网购电。仅靠2小时内的成本不能完整评估新启停的后续影响。实际状态偏离启停计划或计划无法执行时，应触发长周期重算/调度处理，不能强行套用旧状态。每轮以现场新数据校正起点，后续7段允许在下一轮修订。

举例：10:00采集截点后启动计算，候选计划覆盖10:15至12:15；10:15收到下一批数据后启动下一轮，候选计划覆盖10:30至12:30。每次计算8个时段，仅最近的待生效时段作为当前执行参考，后面7段为可修订计划。所有时间在接口中使用UTC，页面明确标注或转换显示。正在执行的区间保留已生效计划；测量截点至新窗口起点之间的衔接也必须纳入约束校验。

## 拟新增接口

不直接改变现有 `/api/v1/fluxcast/compute` 自然日96点约定。以下路径和字段是待确认的新接口设计，不代表平台已采用。

### 1. 实际状态输入：POST /api/v1/fluxcast/actuals

一个快照覆盖七站和19个新能源场站。字段建议：

- `snapshot_id`：上游唯一快照编号；同编号同内容幂等，同编号不同内容拒绝。
- `thermal`：七站记录，每项有 `station_code`、`measured_at`（UTC）、`power_mw`。
- 燃机场站状态同时带 `running`、`state_since`、当前运行日已启动/停机次数；若来自历史采样推导，应标注来源，不能首次上报时默认全部为0。
- `renewable`：19站记录，每项有 `farm_id`、`measured_at`、`power_mw`、`curtailed`（是否已知限发）；可用上限已知时提供 `available_power_mw`。
- 接收方保存测量时间和接收时间；禁止旧快照覆盖新快照，不把不同时间的测量无条件认作同时采集。
- 功率单位MW，时间采用UTC。输入质量处理和实际使用的替代值均记录工作日志；过期实测不得无限沿用并标为最新状态。

第一版建议测量年龄不超过5分钟、各站时间跨度不超过1分钟才参与新一轮计算。作为接口配置项，应根据上游真实上报频率确认；不满足时保留旧结果供查看并标明本轮未更新。

### 2. 滚动计算：POST /api/v1/fluxcast/rolling/compute

- `request_id`：本轮唯一标识，防止重试重复发布。
- `actual_snapshot_id`：引用已保存、可追溯的实测快照。
- `window_start`：新的15分钟边界，UTC，须晚于数据截点并预留求解时间。
- `forecast_batch_id`：引用本轮预测版本。
- `forecast_frames`：从window_start起8个15分钟时段，包含七站预测出力。
- `renewable_data`：覆盖同一窗口的19站可用功率预测，按绝对时间对齐原生predictedTime；不是固定取某一个timeSeries。
- 引用已生效计划用于衔接，并记录计划版本，防止并发请求用旧版本覆盖新版本。
- 引用长周期启停计划版本及其在本窗口内的计划状态，作为近期出力优化约束；与实测不一致时明确返回需要重规划的状态。

返回新计划版本、计算时间、有效起止时间及8时段结果。功率、成本等成功结果值仍为有限浮点数；无法计算返回错误状态，不返回null调度指令。实际字段结构需在新接口协议中明确，不挤入原接口固定result_point结构。实际数据输入与滚动计算逻辑分开，服务在新实测和匹配预测均齐备时触发本轮计算，并按快照/预测/长周期计划版本记录完整关联。

## 预测和需求口径

当前代码以七站原始功率曲线之和作为等效需求。在新功能第一版中，可沿用“七站预测出力之和作为等效需求”的场景定义；应明确这是替代调度目标，不声称它是独立的用户负荷预测。

七站实测功率用于确定计算起点，不反过来替换整条未来需求曲线，也不把新能源实测再次加到上述等效需求中造成重复计入。后续若平台提供独立需求预测，应使用单独字段和明确的供需边界。

已有固定一天的96点可按绝对时间切取本轮需要的8点，作为测试用预测。窗口滚动到数据覆盖范围之外时需要新增预测尾部点；没有跨日预测时不能循环复制原曲线冒充新预测。历史回放可用明确标注的历史后续片段验证流程。

新能源实测用于偏差分析和近期预测修正的依据，但不能直接将实测发电功率当成可用出力上限。已知限发时，低实测值不能用来降低可用功率预测。第一版优先采用上游更新的短期预测或明确提供的可用功率信息；缺少这些信息时保留原预测并注明来源，不自行构造未经校验的全天修正规则。

## 模型必须补充的内容

1. 初始功率改用本轮实际状态，不再取预测曲线第一个值；不能通过静默夹紧实测值来假装初始状态满足约束。
2. 继承已连续开停机时长，约束剩余最小开停机时间。
3. 已发生启停次数按实际运行日累计；滚动到午夜时按运行日分组，不能将“每窗口最多一次”误当“每日最多一次”。运行日时区需要明确配置，不能仅因传输时间用UTC就自动改变业务日口径。
4. 正在执行区间和测量至生效时刻之间的衔接需受爬坡和状态约束；新结果只能改变生效时刻之后的计划。
5. 碳约束及基准成本使用同一预测窗口、相同需求和一致的初始状态。滚动窗口计划总量不能直接和旧自然日总量比较。
6. 长周期层负责启停安排，近期层负责8时段出力分配。窗口末端持续开停机义务必须继承；终端出力需衔接后续计划，不能声称2小时窗口能保证之后所有时段可行。
7. 先实现并验证现有HiGHS路径；其他求解器在约束未同步前不作为滚动接口的可选后端。

## 发布、展示与异常处理

- 实测上报与求解分离；求解按窗口串行或受控并发，同一窗口只发布通过校验且未过期的新版本。
- 输出为调度建议，不在本次范围内直接下发到电厂控制系统。
- 页面显示实际出力、预测出力、优化出力、计划与实际偏差，以及各自时间/批次。
- 累计实际量依据测量或电量计量数据计算；计划累计来自明确选定的计划版本。不能把多个重叠2小时窗口的合计相加。全天展示可保留原全天计划作为参考，逐轮替换未来覆盖段并标明版本，已发生实际量单独保存。实测若为瞬时功率，其15分钟间隔积分只是估算；优先使用区间平均功率或电能计量数据计算实际电量。
- 新计算失败、输入陈旧或超时：记录工作日志，保留上一版本供查看并标识本轮失败；是否继续执行旧指令由现有调度流程决定，不自动宣称旧计划仍可执行。

## 实施验证范围

以历史数据回放连续至少一个跨午夜窗口，检查实际快照替换、首段衔接、剩余开停机时间、每日启停次数、预测跨日取点、重复/乱序请求、晚到结果拒绝发布，以及展示中实际/计划累计不混淆。先完成回放验证，再接真实上游进行联调。

当前需要平台提供或明确：实际状态输入来源、运行日时区、状态历史和连续跨日的预测供给。以上在真实接入前确认；本草案不声称这些数据已具备。
