## 范围与结论

依据用户提供的《测试报告-新能源预测数据联调-20260918.md》、renewable_20260918.tar.gz 和当前本地封装。报告中的建议属于待确认的接口方案，不等同于已经实现或批准的契约。

本轮只做数据审计和隔离复现，没有修改原始预测、容量表、生产接口、output/final 或展示网站。未访问报告中的内网预测服务，也未在 Kylin ARM 主机上验收。

结论：本地默认 HiGHS 可以实际求解；原始新能源长表与当前封装的宽表 HTTP 契约不兼容；首日存在容量超限；报告中的备用批次选择及部分空值输出方案还需要澄清。

## 需要明确的契约

1. 若采用平台透传，新增可选renewable_data并保留旧HTTP宽表模式；明确两种输入同时存在时的优先级或拒绝规则。上游预测系统无需改动。
2. 以目标调度日与转换后的时间戳选取19场×96点，并校验批次一致、重复点和缺失点。不要无条件固定timeSeries=1：使用前一发布批次时，目标日通常在timeSeries=2；首日过滤会取错日期。
3. 不根据单批文件推断每天08:00固定发布。批次发布、更新、回退和同日重算规则由双方确认；当前完成批次不会默默被新输入覆盖。
4. 容量须确认康保实际值和预测覆盖范围。若业务批准限幅，应保留原始值、限幅后的调度可用值和质量说明，不能改原始文件或把超限数值直接送入调度。
5. 缺失某个新能源场站或燃机输入会影响全局功率平衡与联合调度，不能默认只让单站结果为空而其余优化指令仍有效。若平台需要null，应先约定失败状态、HTTP状态、result_point结构和日志字段；不得标记completed或填零冒充成功。
6. 七个燃机场站请求（source_id）与十九个新能源farmId是不同维度；新能源数据若随请求透传，应明确是在七站请求中保持同一份数据。
